=== THE ONE REAL DEFECT ===

/home/lnicoara/build/mine.d/fs2.d/fs2/src/math/vecmat.cc:1622: note: `ix = 1.0f / rot_axis->x` reads the OUTPUT vector two lines before that component is written -- uninitialised stack read
/home/lnicoara/build/mine.d/fs2.d/fs2/src/math/vecmat.cc:1624: note: this is where rot_axis->x actually gets its value; the reciprocal above needed to come AFTER it
/home/lnicoara/build/mine.d/fs2.d/fs2/src/math/vecmat.cc:1632: note: same defect, case 1 (iy from an unwritten rot_axis->y)
/home/lnicoara/build/mine.d/fs2.d/fs2/src/math/vecmat.cc:1642: note: same defect, case 2 (iz from an unwritten rot_axis->z)

vm_matrix_to_rot_axis_and_angle's theta==PI branch.  At exactly 180 deg
the rotation axis is degenerate, so the routine reconstructs it from the
largest diagonal term.  All three cases take the reciprocal of the axis
component BEFORE computing it, so the scale factor comes from whatever
was on the stack.  Result: a NaN axis.

Measured, not inferred.  A temporary probe at the call site printed:

    NANPROBE theta 3.14159 axis -nan -nan -nan goal -nan -nan -nan
    NANPROBE curr 0.329988 0.413277 0.848711 / -0.874826 0.471676 ...
    NANPROBE goal -0.0105273 0.990426 0.137641 / 0.978091 -0.018421 ...

theta is pi to six figures; the axis is NaN.  (Probe reverted; tree clean.)

How the NaN reaches the assert:

/home/lnicoara/build/mine.d/fs2.d/fs2/src/math/vecmat.cc:1879: note: theta_goal = rot_axis * theta -- a NaN axis makes every component NaN
/home/lnicoara/build/mine.d/fs2.d/fs2/src/math/vecmat.cc:1891: note: the per-axis dispatch sign-corrects so away() always sees theta_goal >= 0 ... but NaN fails BOTH `> 0` and `< 0` and falls through to the "theta_goal == 0" branch
/home/lnicoara/build/mine.d/fs2.d/fs2/src/math/vecmat.cc:1824: note: Assert(theta_goal >= 0) -- fires on NaN, which is why a routine that cannot be handed a negative still aborts

The dispatch's careful sign correction is exactly what disguises the
bug: a negative theta_goal is genuinely unreachable, so the assert reads
as dead code until a NaN walks in through the one comparison hole.

The fix, from fs2open release_26_0_0 code/math/vecmat.cpp:1781-1814 --
compute the sqrt first, then the reciprocal:

    case 0:
        float ix;
        rot_axis->xyz.x = fl_sqrt(m->a2d[0][0] + 1.0f);
        ix = 1.0f / rot_axis->xyz.x;
        rot_axis->xyz.y = m->a2d[0][1] * ix;
        rot_axis->xyz.z = m->a2d[0][2] * ix;
        break;

fs2open also dropped the per-case vm_vec_normalize calls.  That part is
cleanup, NOT a second bug: ours already normalises after the switch at
vecmat.cc:1654, so cases 0 and 1 merely normalise twice.  Case 2 is fine.

NOT yet fixed here -- this sweep's scope was the ledger.


=== NON-DEFECTS, RECORDED SO THEY ARE NOT RE-CHASED ===

loop2-2 reports no player ship in any state line.  Not a bug: Alpha 1
(sig 8) is created at frame 1 and destroyed at frame 584.  The player
simply dies, because the mission is a four-Mara suicide run at a
Sathanas and nobody is flying.

16 of loop2-2's 40 object creations cross the boundary with an EMPTY
name.  Not a bug: the events() filter admits OBJ_WEAPON, OBJ_FIREBALL,
OBJ_DEBRIS and OBJ_SHOCKWAVE beside ships, and those legitimately have
no ship name.  The sweep's "crt"/"dst" columns therefore count all
object churn, not ship arrivals -- which is why SM2-09 shows 1517
creations in 60 s.

Warning volume is model-table chatter, not simulation trouble.  The
three shapes, in descending count:

  "Estimated radius error: Estimate X, actual Y Mc->radius"
      208 in SM1-09 alone -- a per-instance model radius estimate,
      emitted once per created object of the offending classes
  "Warning: Ignoring unrecognized subsystem <name>, believed to be in
   ship <pof>"  -- e.g. fighterbay on capital01b.pof, core on
      Comm2S-01.pof; retail's own tables vs its own models
  "Unknown special object type $pathNN while reading model <pof>"

Every mission also emits a constant baseline the sweep filters out:
"Weapon name -- Unknown Bomb/Megabomb", "Error opening mission.txt",
"Error opening hud config file".


=== WHAT THIS SWEEP DOES NOT ESTABLISH ===

Hands-off for 60 s is a smoke test, not a playthrough.  It does not
touch: whether goals can be MET, whether the campaign advances
mission-to-mission on real outcomes, arrivals cued minutes in, or
anything past the first minute of each mission.  A mission that boots
clean here can still be unplayable.


=== HOW TO RE-RUN ===

The sweep script is scratch, not a gate:
  <session scratchpad>/sweep.py

  python3 sweep.py [frames]          # default 3600

It reads the mission list straight out of the install's FreeSpace2.fc2,
so it tracks the campaign rather than a copied list.  If it earns a
place it becomes a gate; for now it is an instrument.

Single mission, by hand:

  ./build/libfs2/sim_dump ../rundir SM2-02.fs2 run 3600 1800
